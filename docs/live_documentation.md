# Жива документація проєкту

## 1. Загальна ідея

Жива документація — це опис поведінки системи, який підтримується разом із кодом і відображає реальні сценарії використання застосунку.

У цьому проєкті жива документація формується на основі:

- BDD-сценаріїв Cucumber;
- E2E-сценаріїв Playwright;
- Swagger / OpenAPI-документації backend API;
- JSDoc-коментарів у frontend і backend коді;
- ручних smoke-test сценаріїв для перевірки повного користувацького потоку.

Оскільки проєкт активно змінювався, застарілі тести для файлового JSON-сховища користувачів були видалені. Актуальна поведінка системи тепер описує роботу з PostgreSQL, backend API, JWT-авторизацією, модерацією, коментарями, обраним, прогресом читання та статистикою.

---

## 2. Джерела живої документації

У проєкті використовуються такі джерела живої документації:

- `my-app/features/*.feature` — BDD-сценарії користувацької поведінки;
- `my-app/features/steps/*.js` — кроки для Cucumber-сценаріїв;
- `my-app/features/support/*.js` — налаштування тестового середовища;
- `server/docs/swagger.js` — опис Swagger / OpenAPI;
- `server/docs/api/openapi.json` — згенерована OpenAPI-специфікація;
- JSDoc-коментарі у файлах `my-app/src` та `server`;
- документаційні файли у папці `docs`;
- ручний smoke-test повного користувацького сценарію.

## 3. Frontend BDD / E2E-сценарії

Frontend-сценарії розташовані у папці:

```text
my-app/features
```

Основні feature-файли:

```text
my-app/features/authentication.feature
my-app/features/search.feature
```

Ці файли описують поведінку застосунку мовою, близькою до користувацьких сценаріїв.

---

## 4. Authentication feature

Файл:

```text
my-app/features/authentication.feature
```

Документує поведінку авторизації на рівні інтерфейсу.

Типові сценарії:

- відкриття застосунку;
- перехід на сторінку входу;
- введення логіна або email;
- введення пароля;
- надсилання форми входу;
- перевірка переходу після логіну;
- перевірка доступу до захищених сторінок.

Ці сценарії підтверджують, що користувач може взаємодіяти з frontend-формами авторизації та отримувати доступ до приватних сторінок після входу.

---

## 5. Search feature

Файл:

```text
my-app/features/search.feature
```

Документує поведінку пошуку і фільтрації на головній сторінці.

Типові сценарії:

- відкриття головної сторінки;
- введення пошукового запиту;
- фільтрація творів за назвою;
- перевірка результатів пошуку;
- взаємодія з каталогом творів.

Після переходу на backend API головна сторінка отримує твори з PostgreSQL через `/api/works`. Локальний `works.json` більше не використовується як fallback.

## 6. Step definitions

Кроки для BDD-сценаріїв розташовані у папці:

```text
my-app/features/steps
```

Основний файл:

```text
my-app/features/steps/ui.steps.js
```

Цей файл описує технічну реалізацію кроків із `.feature`-файлів.

Приклади дій, які виконуються у step definitions:

- відкриття сторінки;
- натискання на посилання або кнопку;
- введення тексту в поле;
- надсилання форми;
- очікування переходу;
- перевірка наявності тексту на сторінці;
- перевірка результатів пошуку.

Таким чином `.feature`-файли описують сценарій зрозумілою мовою, а `ui.steps.js` пов’язує ці сценарії з реальними діями у браузері.

Допоміжні файли розташовані у папці:

## 8. GitHub Actions для E2E

У проєкті є workflow:

```text
.github/workflows/e2e-cucumber.yml
```

Він описує автоматичний запуск E2E-перевірок.

Основні кроки workflow:

1. checkout репозиторію;
2. встановлення Node.js;
3. встановлення backend-залежностей;
4. встановлення frontend-залежностей;
5. встановлення Playwright browsers;
6. запуск backend;
7. запуск frontend;
8. очікування доступності UI;
9. запуск Cucumber-сценаріїв;
10. завантаження reports і logs як artifact.

Цей workflow дозволяє використовувати BDD/E2E-сценарії як автоматичну живу документацію користувацьких сценаріїв. :contentReference[oaicite:1]{index=1}

## 9. Swagger / OpenAPI як документація API

Backend має Swagger / OpenAPI-документацію.

Основні файли:

```text
server/docs/swagger.js
server/docs/api/openapi.json
server/scripts/generate-openapi.js
```

Swagger-документація описує:

- доступні API routes;
- HTTP-методи;
- структуру запитів;
- структуру відповідей;
- можливі помилки;
- авторизацію через Bearer token.

У запущеному backend Swagger UI доступний за адресою:

```text
/api/docs
```

OpenAPI JSON доступний за адресою:

```text
/api/docs.json
```

## 10. Основні API-напрямки

Актуальні API-напрямки системи:

```text
/api/auth
/api/works
/api/comments
/api/me
/api/admin
/api/health
/api/docs
```

### `/api/auth`

Документує:

- реєстрацію користувача;
- логін користувача;
- отримання поточного користувача за JWT.

### `/api/works`

Документує:

- отримання опублікованих творів;
- отримання одного твору;
- створення твору;
- редагування твору;
- видалення твору;
- отримання власних творів;
- отримання творів на модерації;
- підтвердження твору;
- відхилення твору.

### `/api/comments`

Документує:

- отримання коментарів до твору;
- створення коментаря;
- редагування коментаря;
- видалення коментаря;
- лайк або зняття лайка з коментаря;
- отримання коментарів поточного користувача.

### `/api/me`

Документує персональну активність користувача:

- обрані твори;
- прогрес читання;
- улюблені жанри.

### `/api/admin`

Документує адміністративну статистику:

- кількість користувачів;
- кількість творів;
- кількість творів за статусами;
- кількість коментарів;
- кількість лайків;
- кількість додавань в обране;
- кількість записів прогресу читання;
- статистику жанрів;
- статистику авторів;
- останні твори.

### `/api/health`

Документує технічну перевірку доступності backend і PostgreSQL.

Очікувана відповідь:

```json
{
  "ok": true,
  "database": true
}
```

## 11. JSDoc як технічна документація

У frontend і backend коді використовуються JSDoc-коментарі.

Вони описують:

- призначення функцій;
- параметри;
- типи даних;
- значення, що повертаються;
- призначення компонентів;
- призначення middleware;
- призначення API helpers;
- логіку роботи з базою даних.

Генерація документації виконується окремо для frontend і backend.

### Frontend

```bash
cd my-app
npm run docs
```

Результат:

```text
my-app/docs/generated/frontend
```

### Backend

```bash
cd server
npm run docs
```

Результат:

```text
server/docs/generated/backend
```

Generated-документацію не потрібно редагувати вручну. Вона створюється автоматично з JSDoc-коментарів.

## 13. Ручний smoke-test як жива документація

Окрім автоматичних сценаріїв, у проєкті використовується ручний smoke-test повного користувацького потоку.

Цей сценарій корисний після великих змін у backend, frontend або базі даних.

### Повний smoke-test

1. Запустити PostgreSQL.
2. Запустити backend.
3. Перевірити `/api/health`.
4. Запустити frontend.
5. Зареєструвати нового користувача.
6. Увійти в акаунт.
7. Створити новий твір.
8. Перевірити, що твір має статус `pending`.
9. Створити або використати користувача з роллю `moderator`.
10. Увійти як модератор.
11. Відкрити сторінку модерації.
12. Підтвердити твір.
13. Перевірити, що твір з’явився на головній сторінці.
14. Відкрити сторінку твору.
15. Перейти на іншу сторінку читання.
16. Перевірити, що прогрес читання зберігся.
17. Додати твір в обране.
18. Додати коментар і оцінку.
19. Перевірити рейтинг твору.
20. Перейти в кабінет.
21. Перевірити власні твори, обране, прогрес читання і коментарі.
22. Вибрати улюблені жанри.
23. Перейти на головну сторінку.
24. Перевірити рекомендоване сортування.
25. Відкрити сторінку статистики.
26. Перевірити, що статистика рахується з PostgreSQL.

## 14. Перевірка даних у PostgreSQL

Для підтвердження сценаріїв можна використовувати SQL-запити.

### Користувачі

```sql
SELECT id, login, email, role, created_at
FROM users
ORDER BY id DESC;
```

### Твори

```sql
SELECT id, title, author_id, status, created_at, updated_at
FROM works
ORDER BY id DESC;
```

### Коментарі

```sql
SELECT id, work_id, user_id, rating, created_at
FROM comments
ORDER BY id DESC;
```

### Обране

```sql
SELECT *
FROM favorite_works
ORDER BY id DESC;
```

### Прогрес читання

```sql
SELECT *
FROM reading_progress
ORDER BY updated_at DESC;
```

### Улюблені жанри

```sql
SELECT *
FROM favorite_genres
ORDER BY id DESC;
```

## 16. Як підтримувати живу документацію актуальною

Після кожної суттєвої зміни потрібно:

1. оновити BDD-сценарії, якщо змінився користувацький flow;
2. оновити step definitions, якщо змінилась структура сторінок;
3. оновити Swagger/OpenAPI, якщо змінився backend API;
4. оновити JSDoc, якщо змінились функції або модулі;
5. оновити smoke-test, якщо додано новий важливий сценарій;
6. перегенерувати JSDoc-документацію;
7. перегенерувати OpenAPI JSON;
8. перевірити, що документація не містить застарілих згадок про видалені модулі.

## 18. Висновок

Жива документація у проєкті складається не з одного файлу, а з набору пов’язаних джерел:

- BDD-сценаріїв;
- step definitions;
- Swagger/OpenAPI;
- JSDoc;
- ручного smoke-test сценарію;
- SQL-перевірок.

Разом вони описують як технічну, так і користувацьку поведінку системи.

Актуальна версія живої документації відображає перехід проєкту на PostgreSQL, backend API, JWT-авторизацію, модерацію творів, коментарі, обране, прогрес читання, улюблені жанри та адміністративну статистику.
