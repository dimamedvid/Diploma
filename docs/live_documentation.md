# Жива документація проєкту

## 1. Загальна ідея

Жива документація — це опис поведінки системи, який підтримується разом із кодом і відображає реальні сценарії використання застосунку.

У цьому проєкті жива документація формується на основі:

- BDD-сценаріїв Cucumber;
- E2E-сценаріїв Playwright;
- Swagger / OpenAPI-документації backend API;
- JSDoc-коментарів у frontend і backend коді;
- ручних smoke-test сценаріїв для перевірки повного користувацького потоку;
- SQL-перевірок даних у PostgreSQL.

Актуальна поведінка системи описує роботу з PostgreSQL, backend API, JWT-авторизацією, модерацією, коментарями, обраним, прогресом читання, улюбленими жанрами, публічними профілями користувачів та адміністративною статистикою.

---

## 2. Джерела живої документації

У проєкті використовуються такі джерела живої документації:

- `my-app/features/*.feature` — BDD-сценарії користувацької поведінки;
- `my-app/features/steps/*.js` — кроки для Cucumber-сценаріїв;
- `my-app/features/support/*.js` — налаштування тестового середовища;
- `server/docs/swagger.js` — опис Swagger / OpenAPI;
- `server/docs/api/openapi.json` — згенерована OpenAPI-специфікація;
- JSDoc-коментарі у файлах `my-app/src` та `server`;
- документаційні файли у папці `docs`;
- ручний smoke-test повного користувацького сценарію;
- SQL-запити для перевірки стану даних у PostgreSQL.

## 3. Frontend BDD / E2E-сценарії

Frontend-сценарії розташовані у папці:

```text
my-app/features
```

Основні feature-файли:

```text
my-app/features/authentication.feature
my-app/features/search.feature
```

Ці файли описують поведінку застосунку мовою, близькою до користувацьких сценаріїв.

## 4. Authentication feature

Файл:

```text
my-app/features/authentication.feature
```

Документує поведінку авторизації на рівні інтерфейсу.

Типові сценарії:

- відкриття застосунку;
- перехід на сторінку входу;
- введення логіна або email;
- введення пароля;
- надсилання форми входу;
- перевірка переходу після логіну;
- перевірка доступу до захищених сторінок.

Ці сценарії підтверджують, що користувач може взаємодіяти з frontend-формами авторизації та отримувати доступ до приватних сторінок після входу.

## 5. Search feature

Файл:

```text
my-app/features/search.feature
```

Документує поведінку пошуку і фільтрації на головній сторінці.

Типові сценарії:

- відкриття головної сторінки;
- введення пошукового запиту;
- фільтрація творів за назвою;
- перевірка результатів пошуку;
- взаємодія з каталогом творів.

Після переходу на backend API головна сторінка отримує твори з PostgreSQL через:

```text
GET /api/works
```

## 6. Step definitions

Кроки для BDD-сценаріїв розташовані у папці:

```text
my-app/features/steps
```

Основний файл:

```text
my-app/features/steps/ui.steps.js
```

Цей файл описує технічну реалізацію кроків із `.feature`-файлів.

Приклади дій, які виконуються у step definitions:

- відкриття сторінки;
- натискання на посилання або кнопку;
- введення тексту в поле;
- надсилання форми;
- очікування переходу;
- перевірка наявності тексту на сторінці;
- перевірка результатів пошуку.

Таким чином `.feature`-файли описують сценарій зрозумілою мовою, а `ui.steps.js` пов’язує ці сценарії з реальними діями у браузері.

## 8. GitHub Actions для E2E

У проєкті є workflow:

```text
.github/workflows/e2e-cucumber.yml
```

Він описує автоматичний запуск E2E-перевірок.

Основні кроки workflow:

1. checkout репозиторію;
2. встановлення Node.js;
3. встановлення backend-залежностей;
4. встановлення frontend-залежностей;
5. встановлення Playwright browsers;
6. запуск backend;
7. запуск frontend;
8. очікування доступності UI;
9. запуск Cucumber-сценаріїв;
10. завантаження reports і logs як artifact.

Цей workflow дозволяє використовувати BDD/E2E-сценарії як автоматичну живу документацію користувацьких сценаріїв.

## 10. Основні API-напрямки

Актуальні API-напрямки системи:

```text
/api/auth
/api/works
/api/comments
/api/me
/api/users
/api/admin
/api/health
/api/docs
```

### `/api/auth`

Документує:

- реєстрацію користувача;
- логін користувача;
- отримання поточного користувача за JWT.

Основні endpoint-и:

```text
POST /api/auth/register
POST /api/auth/login
GET  /api/auth/me
```

---

### `/api/works`

Документує:

- отримання опублікованих творів;
- отримання одного твору;
- створення твору;
- редагування твору;
- видалення твору;
- отримання власних творів;
- отримання творів на модерації;
- підтвердження твору;
- відхилення твору.

Основні endpoint-и:

```text
GET    /api/works
GET    /api/works/:id
POST   /api/works
PUT    /api/works/:id
DELETE /api/works/:id
GET    /api/works/me
GET    /api/works/moderation/pending
PATCH  /api/works/:id/approve
PATCH  /api/works/:id/reject
```

---

### `/api/comments`

Документує:

- отримання коментарів до твору;
- створення коментаря;
- редагування коментаря;
- видалення коментаря;
- лайк або зняття лайка з коментаря;
- отримання коментарів поточного користувача.

Основні endpoint-и:

```text
GET    /api/comments/work/:workId
POST   /api/comments/work/:workId
PUT    /api/comments/:commentId
DELETE /api/comments/:commentId
POST   /api/comments/:commentId/like
GET    /api/comments/me
```

---

### `/api/me`

Документує персональну активність користувача:

- отримання обраних творів;
- додавання твору в обране;
- видалення твору з обраного;
- отримання прогресу читання;
- збереження прогресу читання;
- видалення прогресу читання;
- отримання улюблених жанрів;
- збереження улюблених жанрів.

Основні endpoint-и:

```text
GET    /api/me/favorite-works
POST   /api/me/favorite-works/:workId/toggle

GET    /api/me/reading-progress
PUT    /api/me/reading-progress/:workId
DELETE /api/me/reading-progress/:workId

GET    /api/me/favorite-genres
PUT    /api/me/favorite-genres
```

---

### `/api/users`

Документує публічні профілі користувачів:

- отримання профілю користувача;
- отримання його опублікованих творів;
- перегляд базової статистики профілю;
- відкриття профілю через автора твору;
- відкриття профілю через автора коментаря.

Основний endpoint:

```text
GET /api/users/:id/profile
```

Профіль користувача містить:

- ID користувача;
- логін;
- ім’я та прізвище;
- повне ім’я для відображення;
- роль;
- дату реєстрації;
- список опублікованих творів;
- кількість опублікованих творів;
- кількість коментарів;
- кількість додавань в обране.

Публічний профіль не повертає приватні дані користувача, наприклад пароль або `password_hash`.

---

### `/api/admin`

Документує адміністративну статистику:

- кількість користувачів;
- кількість творів;
- кількість творів за статусами;
- кількість коментарів;
- кількість лайків;
- кількість додавань в обране;
- кількість записів прогресу читання;
- статистику жанрів;
- статистику авторів;
- останні твори.

Основний endpoint:

```text
GET /api/admin/stats
```

---

### `/api/health`

Документує технічну перевірку доступності backend і PostgreSQL.

Endpoint:

```text
GET /api/health
```

Очікувана відповідь:

```json
{
  "ok": true,
  "database": true
}
```

## 13. Ручний smoke-test як жива документація

Окрім автоматичних сценаріїв, у проєкті використовується ручний smoke-test повного користувацького потоку.

Цей сценарій корисний після великих змін у backend, frontend або базі даних.

### Повний smoke-test

1. Запустити PostgreSQL.
2. Запустити backend.
3. Перевірити `/api/health`.
4. Запустити frontend.
5. Зареєструвати нового користувача.
6. Увійти в акаунт.
7. Створити новий твір.
8. Перевірити, що твір має статус `pending`.
9. Створити або використати користувача з роллю `moderator`.
10. Увійти як модератор.
11. Відкрити сторінку модерації.
12. Підтвердити твір.
13. Перевірити, що твір з’явився на головній сторінці.
14. Відкрити сторінку твору.
15. Натиснути на автора твору і перевірити відкриття профілю користувача.
16. Повернутися до сторінки твору.
17. Перейти на іншу сторінку читання.
18. Перевірити, що прогрес читання зберігся.
19. Додати твір в обране.
20. Перейти в кабінет.
21. Перевірити, що твір з’явився у списку обраного.
22. Натиснути кнопку `Видалити з обраного`.
23. Перевірити, що твір зник зі списку обраного.
24. Перезавантажити сторінку кабінету.
25. Перевірити, що твір не повернувся до списку обраного.
26. Повернутися до сторінки твору.
27. Додати коментар і оцінку.
28. Перевірити рейтинг твору.
29. Натиснути на автора коментаря і перевірити відкриття профілю користувача.
30. Перейти в кабінет.
31. Перевірити власні твори, коментарі та прогрес читання.
32. Вибрати улюблені жанри.
33. Перейти на головну сторінку.
34. Перевірити рекомендоване сортування.
35. Відкрити сторінку статистики.
36. Перевірити, що статистика рахується з PostgreSQL.
37. Перевірити адаптивність основних сторінок на мобільній ширині екрана.

## 15. Перевірка даних у PostgreSQL

Для підтвердження сценаріїв можна використовувати SQL-запити.

### Користувачі

```sql
SELECT id, login, email, role, created_at
FROM users
ORDER BY id DESC;
```

### Твори

```sql
SELECT id, title, author_id, status, rejection_reason, created_at, updated_at
FROM works
ORDER BY id DESC;
```

### Коментарі

```sql
SELECT id, work_id, user_id, rating, created_at
FROM comments
ORDER BY id DESC;
```

### Обране

```sql
SELECT *
FROM favorite_works
ORDER BY id DESC;
```

### Прогрес читання

```sql
SELECT *
FROM reading_progress
ORDER BY updated_at DESC;
```

### Улюблені жанри

```sql
SELECT *
FROM favorite_genres
ORDER BY id DESC;
```

## 17. Як підтримувати живу документацію актуальною

Після кожної суттєвої зміни потрібно:

1. оновити BDD-сценарії, якщо змінився користувацький flow;
2. оновити step definitions, якщо змінилась структура сторінок;
3. оновити Swagger/OpenAPI, якщо змінився backend API;
4. оновити JSDoc, якщо змінились функції або модулі;
5. оновити smoke-test, якщо додано новий важливий сценарій;
6. оновити SQL-перевірки, якщо змінилася структура БД;
7. перегенерувати JSDoc-документацію;
8. перегенерувати OpenAPI JSON;
9. перевірити, що документація не містить застарілих згадок про видалені модулі.

## 19. Ознаки актуальної живої документації

Жива документація є актуальною, якщо:

- smoke-test відповідає реальному функціоналу застосунку;
- Swagger / OpenAPI описує актуальні backend routes;
- JSDoc-коментарі відповідають поточним функціям;
- BDD-сценарії не посилаються на видалені сторінки або стару логіку;
- документація описує PostgreSQL як основне сховище даних;
- документація описує публічні профілі користувачів;
- документація описує видалення твору з обраного через кабінет;
- документація не містить застарілих згадок про локальні JSON-сховища.

- BDD-сценаріїв;
