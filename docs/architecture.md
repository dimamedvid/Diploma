# Архітектурні рішення та взаємодія компонентів

## 1. Загальна архітектура

Проєкт складається з двох основних частин:

- `my-app` — клієнтська частина на React;
- `server` — серверна частина на Node.js, Express та PostgreSQL.

Frontend відповідає за відображення інтерфейсу, маршрутизацію, роботу з формами, пошук, фільтрацію, керування станом авторизації та взаємодію з backend API.

Backend відповідає за авторизацію, роботу з базою даних, модерацію творів, коментарі, оцінки, обране, прогрес читання, улюблені жанри та адміністративну статистику.

Дані системи зберігаються у PostgreSQL. Файлове JSON-сховище для користувачів більше не використовується.

---

## 2. Основні компоненти системи

### Frontend

Клієнтська частина розташована у папці `my-app`.

Основні частини frontend:

- `App.js` — маршрутизація застосунку та загальний layout;
- `Header.js`, `Footer.js` — спільні елементи інтерфейсу;
- `HomePage.js` — головна сторінка каталогу творів;
- `LoginPage.js`, `RegisterPage.js` — сторінки авторизації;
- `CabinetPage.js` — особистий кабінет користувача;
- `CreateWorkPage.js` — створення нового твору;
- `EditWorkPage.js` — редагування твору;
- `WorkDetailsPage.js` — перегляд твору, читання сторінок, коментарі та обране;
- `AdminPage.js` — сторінка модерації творів;
- `AdminStatsPage.js` — сторінка статистики адміністратора;
- `ProtectedRoute.js` — захист маршрутів для авторизованих користувачів;
- `AdminRoute.js` — захист маршрутів для модератора або адміністратора;
- `authSlice.js` — збереження поточного користувача та JWT-токена у Redux/localStorage;
- `api/*.js` — модулі для HTTP-запитів до backend API.

### Backend

Серверна частина розташована у папці `server`.

Основні частини backend:

- `index.js` — ініціалізація Express-сервера, middleware та API routes;
- `routes/auth.routes.js` — реєстрація, логін та отримання поточного користувача;
- `routes/work.routes.js` — створення, редагування, видалення, модерація та перегляд творів;
- `routes/comment.routes.js` — коментарі, оцінки та лайки коментарів;
- `routes/userActivity.routes.js` — обране, прогрес читання та улюблені жанри;
- `routes/adminStats.routes.js` — статистика для адміністратора або модератора;
- `middlewares/auth.middleware.js` — перевірка JWT-токена;
- `middlewares/errorHandler.js` — централізована обробка помилок;
- `utils/db.js` — підключення до PostgreSQL, SQL-запити та транзакції;
- `utils/userDb.js` — робота з таблицею користувачів;
- `utils/workDb.js` — робота з творами та сторінками творів;
- `utils/commentDb.js` — робота з коментарями, оцінками та лайками;
- `utils/userActivityDb.js` — робота з обраним, прогресом читання та жанрами;
- `utils/adminStatsDb.js` — SQL-запити для адміністративної статистики;
- `utils/AppError.js` — клас контрольованих помилок API;
- `utils/logger.js` — логування.

## 3. База даних

У проєкті використовується PostgreSQL.

Основні таблиці:

- `users` — користувачі системи;
- `works` — літературні твори;
- `work_pages` — сторінки творів;
- `comments` — коментарі та оцінки;
- `comment_likes` — лайки коментарів;
- `favorite_works` — обрані твори користувачів;
- `reading_progress` — прогрес читання;
- `favorite_genres` — улюблені жанри користувачів.

Ключові зв’язки:

- `works.author_id` посилається на `users.id`;
- `comments.user_id` посилається на `users.id`;
- `comments.work_id` посилається на `works.id`;
- `comment_likes.user_id` посилається на `users.id`;
- `comment_likes.comment_id` посилається на `comments.id`;
- `favorite_works.user_id` посилається на `users.id`;
- `favorite_works.work_id` посилається на `works.id`;
- `reading_progress.user_id` посилається на `users.id`;
- `reading_progress.work_id` посилається на `works.id`;
- `favorite_genres.user_id` посилається на `users.id`.

Для створення актуальної схеми використовується SQL-файл:

```text
server/scripts/reset-auth-and-user-relations.sql
```

## 4. Авторизація та ролі

Авторизація побудована на JWT-токенах.

Під час реєстрації:

1. користувач вводить логін, email, пароль, ім’я та прізвище;
2. backend перевіряє обов’язкові поля;
3. backend перевіряє унікальність логіна та email у таблиці `users`;
4. пароль хешується за допомогою `bcryptjs`;
5. користувач зберігається у PostgreSQL;
6. backend повертає дані користувача та JWT-токен.

Під час логіну:

1. користувач вводить логін/email та пароль;
2. backend знаходить користувача в таблиці `users`;
3. пароль перевіряється через `bcrypt.compare`;
4. backend повертає дані користувача та JWT-токен.

У системі використовуються ролі:

- `user` — звичайний користувач;
- `moderator` — модератор;
- `admin` — адміністратор.

Захищені маршрути frontend перевіряються через Redux-стан авторизації.

Захищені маршрути backend перевіряються через `authMiddleware`.

## 5. Основні API-напрямки

Backend має такі основні групи API:

```text
/api/auth
/api/works
/api/comments
/api/me
/api/admin
/api/docs
/api/health
```

### `/api/auth`

Відповідає за:

- реєстрацію;
- логін;
- отримання поточного користувача за токеном.

### `/api/works`

Відповідає за:

- отримання списку опублікованих творів;
- отримання одного твору;
- створення твору;
- редагування твору;
- видалення твору;
- отримання власних творів;
- отримання творів на модерації;
- підтвердження або відхилення твору.

### `/api/comments`

Відповідає за:

- отримання коментарів до твору;
- створення коментаря;
- редагування коментаря;
- видалення коментаря;
- лайки коментарів;
- отримання коментарів поточного користувача.

### `/api/me`

Відповідає за персональну активність користувача:

- обрані твори;
- прогрес читання;
- улюблені жанри.

### `/api/admin`

Відповідає за адміністративну статистику:

- кількість користувачів;
- кількість творів;
- кількість pending/approved/rejected творів;
- кількість коментарів;
- кількість лайків;
- кількість додавань в обране;
- кількість записів прогресу читання;
- статистику жанрів;
- статистику авторів;
- список останніх творів.

## 6. Логіка роботи з творами

Користувач може створити новий твір через frontend-форму.

Після створення твір отримує статус:

```text
pending
```

Модератор або адміністратор може:

- підтвердити твір;
- відхилити твір;
- вказати причину відхилення.

Статуси творів:

- `pending` — очікує модерації;
- `approved` — опубліковано;
- `rejected` — відхилено.

На головній сторінці відображаються тільки опубліковані твори.

Дані головної сторінки завантажуються з backend API та PostgreSQL. Локальний файл `works.json` більше не використовується як fallback.

---

## 7. Коментарі, оцінки та рейтинг

Користувач може залишити один коментар до одного твору.

Коментар містить:

- текст;
- оцінку від 1 до 5;
- автора;
- дату створення;
- дату оновлення.

Рейтинг твору формується на основі оцінок у коментарях.

Користувач може:

- створити коментар;
- редагувати власний коментар;
- видалити власний коментар;
- поставити або прибрати лайк коментарю.

---

## 8. Обране, прогрес читання та улюблені жанри

Для авторизованого користувача зберігаються:

- список обраних творів;
- поточна сторінка читання для кожного твору;
- до трьох улюблених жанрів.

Ці дані зберігаються у PostgreSQL, а не в localStorage.

Frontend використовує localStorage тільки для збереження поточного auth-стану:

```text
user + token
```

Це дозволяє не втрачати авторизацію після перезавантаження сторінки.

---

## 9. Адміністративна статистика

Сторінка статистики адміністратора завантажує дані з backend route:

```text
GET /api/admin/stats
```

Доступ до цієї сторінки мають тільки користувачі з роллю:

```text
moderator
admin
```

Статистика рахується SQL-запитами з PostgreSQL.

---

## 10. Обробка помилок

Backend використовує централізовану обробку помилок через:

```text
AppError
errorHandler
```

Контрольовані помилки мають:

- HTTP-статус;
- повідомлення;
- ключ локалізації;
- додаткові деталі;
- унікальний `errorId`.

Frontend відображає повідомлення про помилки у відповідних формах та сторінках.

---

## 11. Логування

Backend використовує модуль логування для:

- HTTP-запитів;
- помилок;
- auth-подій;
- перевірки підключення до бази даних;
- адміністративних запитів.

Кожен запит отримує `requestId`, що дозволяє пов’язувати записи у логах.

---

## 12. Взаємодія frontend і backend

Загальний потік роботи виглядає так:

1. користувач відкриває frontend;
2. React Router визначає потрібну сторінку;
3. сторінка викликає відповідний API-модуль з `my-app/src/api`;
4. API-модуль виконує HTTP-запит до backend;
5. backend route обробляє запит;
6. backend helper виконує SQL-запит до PostgreSQL;
7. backend повертає JSON-відповідь;
8. frontend оновлює стан і відображає актуальні дані.

---

## 13. Переваги поточної архітектури

Поточна архітектура має такі переваги:

- дані зберігаються централізовано у PostgreSQL;
- користувачі мають реальні ID з таблиці `users`;
- зв’язки між таблицями контролюються foreign key;
- паролі не зберігаються у відкритому вигляді;
- frontend не залежить від локальних JSON-файлів;
- основний функціонал доступний через backend API;
- модерація, коментарі, обране, прогрес і статистика працюють через базу даних;
- систему простіше розгортати, тестувати і підтримувати.
