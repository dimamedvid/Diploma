# Профілювання та оптимізація продуктивності

## 1. Мета

Метою роботи є дослідження продуктивності вебзастосунку, виявлення вузьких місць у frontend та backend частинах системи, а також підготовка рекомендацій для подальшої оптимізації.

У межах профілювання аналізуються:

- швидкість рендеру frontend-сторінок;
- витрати на пошук, фільтрацію і сортування творів;
- швидкість HTTP-запитів до backend;
- час виконання операцій авторизації;
- робота з PostgreSQL;
- потенційні вузькі місця у SQL-запитах;
- робота сторінки адміністративної статистики;
- використання пам’яті на frontend.

---

## 2. Коротка характеристика проєкту

Проєкт складається з двох основних частин:

- `my-app` — frontend на React;
- `server` — backend на Node.js, Express та PostgreSQL.

Frontend реалізує:

- головну сторінку каталогу творів;
- пошук і фільтрацію;
- сторінки логіну та реєстрації;
- особистий кабінет користувача;
- сторінку створення та редагування твору;
- сторінку читання твору;
- сторінку модерації;
- сторінку адміністративної статистики.

Backend реалізує API для:

- реєстрації та логіну;
- роботи з користувачами;
- створення, редагування, видалення і модерації творів;
- роботи з коментарями, оцінками і лайками;
- обраних творів;
- прогресу читання;
- улюблених жанрів;
- адміністративної статистики;
- перевірки стану сервера і бази даних.

У поточній версії основним сховищем даних є PostgreSQL.

Файлові JSON-сховища для користувачів і творів більше не використовуються в основному runtime-функціоналі.

- `EXPLAIN`;

- аналіз кількості записів у таблицях;
- перевірку часу виконання SQL-запитів.

## 5. Тестові сценарії

### Frontend

Для frontend-частини використовуються такі сценарії:

1. відкриття головної сторінки;
2. завантаження списку творів з backend;
3. введення пошукового запиту;
4. зміна жанру у фільтрі;
5. зміна діапазону рейтингу;
6. сортування творів;
7. відкриття сторінки твору;
8. перемикання сторінок читання;
9. відкриття особистого кабінету;
10. відкриття сторінки статистики.

### Backend

Для backend-частини використовуються такі сценарії:

1. успішна реєстрація нового користувача;
2. невдалий логін;
3. успішний логін існуючого користувача;
4. отримання списку опублікованих творів;
5. створення нового твору;
6. отримання творів на модерації;
7. підтвердження або відхилення твору;
8. створення коментаря;
9. редагування коментаря;
10. додавання твору в обране;
11. збереження прогресу читання;
12. збереження улюблених жанрів;
13. отримання адміністративної статистики;
14. перевірка `/api/health`.

### PostgreSQL

Для бази даних використовуються такі сценарії:

1. перевірка швидкості пошуку користувача за login або email;
2. перевірка швидкості отримання списку approved творів;
3. перевірка JOIN-запиту для отримання твору зі сторінками;
4. перевірка JOIN-запиту для коментарів;
5. перевірка UPSERT для прогресу читання;
6. перевірка агрегатних запитів для статистики;
7. перевірка індексів для foreign key полів.

## 6. Методологія профілювання

Профілювання проводиться окремо для frontend, backend і PostgreSQL.

На frontend досліджуються:

- час рендеру `HomePage`;
- повторні рендери `FiltersBar`;
- час відображення `WorksGrid`;
- час оновлення списку творів після пошуку;
- час відкриття сторінки твору;
- вплив API-запитів на швидкість відображення інтерфейсу.

На backend досліджуються:

- час обробки HTTP-запитів;
- час криптографічної обробки паролів;
- час виконання SQL-запитів;
- час транзакцій;
- час обробки помилок;
- стабільність роботи API при різних сценаріях.

На рівні PostgreSQL досліджуються:

- ефективність запитів;
- використання індексів;
- агрегатні запити;
- JOIN-запити;
- запити до таблиць `users`, `works`, `comments`, `favorite_works`, `reading_progress`, `favorite_genres`.

## 7. Результати базового frontend-профілювання

### 7.1. Відкриття головної сторінки

Під час відкриття головної сторінки основне навантаження створюється:

- завантаженням React-застосунку;
- запитом до backend `/api/works`;
- відображенням списку творів;
- підготовкою даних для фільтрів;
- рендером компонентів `HomePage`, `FiltersBar`, `WorksGrid` і `WorkCard`.

Очікувана поведінка:

- якщо backend доступний, твори завантажуються з PostgreSQL через API;
- якщо backend недоступний, локальні JSON-дані не використовуються;
- користувач бачить повідомлення про недоступність backend.

### 7.2. Пошук і фільтрація

Пошук і фільтрація виконуються на frontend для вже завантаженого списку творів.

Потенційні витрати:

- нормалізація пошукового рядка;
- перевірка назви, автора, жанру і опису;
- фільтрація за рейтингом;
- сортування результатів;
- повторний рендер списку.

Для невеликої кількості творів ця логіка не створює критичного навантаження. При значному зростанні кількості творів частину пошуку і фільтрації доцільно перенести на backend.

### 7.3. Сторінка твору

Сторінка твору завантажує:

- дані твору;
- сторінки твору;
- коментарі;
- статус обраного;
- прогрес читання користувача.

Потенційні вузькі місця:

- завантаження великого тексту твору;
- велика кількість сторінок;
- велика кількість коментарів;
- часте оновлення прогресу читання при перемиканні сторінок.

### 7.4. Особистий кабінет

Особистий кабінет завантажує:

- власні твори користувача;
- коментарі користувача;
- обрані твори;
- прогрес читання;
- улюблені жанри.

Потенційні вузькі місця:

- кілька паралельних API-запитів;
- велика кількість власних творів;
- велика кількість коментарів;
- часте оновлення стану після редагування або видалення.

### 7.5. Сторінка статистики

Сторінка статистики завантажує агреговані дані з backend route:

```text
GET /api/admin/stats
```

Потенційне навантаження створюють SQL-запити з:

- `COUNT`;
- `GROUP BY`;
- `ORDER BY`;
- `LEFT JOIN`;
- `AVG`;
- агрегацією по жанрах;
- агрегацією по авторах;
- отриманням останніх творів.

## 8. Результати базового backend-профілювання

### 8.1. Авторизація

Основні операції під час реєстрації:

1. валідація полів;
2. перевірка унікальності login/email у PostgreSQL;
3. хешування пароля через `bcrypt.hash`;
4. створення запису в таблиці `users`;
5. генерація JWT;
6. повернення відповіді frontend.

Головне потенційне вузьке місце:

```text
bcrypt.hash
```

Ця операція навмисно є відносно дорогою, бо вона захищає паролі користувачів.

### 8.2. Логін

Основні операції під час логіну:

1. пошук користувача за login або email;
2. отримання `password_hash`;
3. перевірка пароля через `bcrypt.compare`;
4. генерація JWT;
5. повернення користувача і токена.

Головне потенційне вузьке місце:

```text
bcrypt.compare
```

SQL-запит пошуку користувача має бути швидким завдяки індексам:

```text
idx_users_login
idx_users_email
```

### 8.3. Отримання списку творів

Запит `/api/works` отримує опубліковані твори з PostgreSQL.

Потенційні витрати:

- фільтрація за `status = 'approved'`;
- сортування;
- підрахунок рейтингу;
- об’єднання з коментарями, якщо рейтинг формується через SQL.

Для цього важливий індекс:

```text
idx_works_status
```

### 8.4. Створення твору

Створення твору включає:

1. перевірку JWT;
2. валідацію полів;
3. створення запису в таблиці `works`;
4. створення сторінок у таблиці `work_pages`;
5. виконання транзакції;
6. повернення створеного твору.

Потенційні вузькі місця:

- велика кількість сторінок;
- довгий текст твору;
- транзакційний запис кількох сторінок;
- помилки валідації великих payload-ів.

### 8.5. Коментарі та рейтинг

Створення коментаря включає:

1. перевірку JWT;
2. перевірку існування твору;
3. перевірку, чи користувач уже коментував цей твір;
4. вставку запису в `comments`;
5. оновлення або перерахунок рейтингу твору.

Потенційні вузькі місця:

- велика кількість коментарів;
- часті оновлення рейтингу;
- JOIN-запити для отримання коментарів разом із лайками.

### 8.6. Обране і прогрес читання

Для обраних творів використовуються таблиці:

```text
favorite_works
reading_progress
favorite_genres
```

Операції мають бути швидкими, бо вони фільтруються за `user_id`.

Важливі індекси:

```text
idx_favorite_works_user_id
idx_reading_progress_user_id
idx_favorite_genres_user_id
```

### 8.7. Адміністративна статистика

Сторінка статистики виконує кілька SQL-запитів паралельно.

Основні операції:

- підрахунок користувачів;
- підрахунок творів;
- підрахунок творів за статусами;
- підрахунок коментарів;
- підрахунок лайків;
- підрахунок обраного;
- підрахунок прогресу читання;
- групування творів за жанрами;
- групування авторів за кількістю творів;
- отримання останніх творів з рейтингом і кількістю коментарів.

Потенційні вузькі місця:

- агрегатні запити на великих таблицях;
- `GROUP BY genre`;
- `GROUP BY author, author_id`;
- `LEFT JOIN comments`;
- `AVG(comments.rating)`;
- `COUNT(comments.id)`.

Для невеликого навчального проєкту це не є критичним. Для великого обсягу даних можна оптимізувати статистику кешуванням або матеріалізованими представленнями.

## 9.1. Основні таблиці

- `users`;

- `reading_progress`;

## 9.2. Основні індекси

Для швидшого пошуку і JOIN-запитів використовуються індекси:

```text
idx_users_login
idx_users_email
idx_works_author_id
idx_works_status
idx_work_pages_work_id
idx_comments_work_id
idx_comments_user_id
idx_comment_likes_comment_id
idx_comment_likes_user_id
idx_favorite_works_user_id
idx_favorite_works_work_id
idx_reading_progress_user_id
idx_reading_progress_work_id
idx_favorite_genres_user_id
```

## 9.3. Приклад перевірки запиту через EXPLAIN

Для перевірки отримання approved творів:

```sql
EXPLAIN ANALYZE
SELECT *
FROM works
WHERE status = 'approved'
ORDER BY created_at DESC;
```

Для перевірки коментарів твору:

```sql
EXPLAIN ANALYZE
SELECT *
FROM comments
WHERE work_id = 1
ORDER BY created_at DESC;
```

Для перевірки прогресу читання користувача:

```sql
EXPLAIN ANALYZE
SELECT *
FROM reading_progress
WHERE user_id = 1
ORDER BY updated_at DESC;
```

Для перевірки статистики жанрів:

```sql
EXPLAIN ANALYZE
SELECT genre, COUNT(id) AS count
FROM works
GROUP BY genre
ORDER BY count DESC, genre ASC;
```

## 11. Потенційні проблеми продуктивності

### Frontend

Потенційні проблеми frontend-частини:

- велика кількість творів може уповільнити фільтрацію;
- великий список `WorkCard` може створювати багато DOM-елементів;
- часті зміни фільтрів можуть викликати багато повторних рендерів;
- сторінка кабінету виконує кілька API-запитів;
- сторінка твору може працювати повільніше при великій кількості коментарів.

### Backend

Потенційні проблеми backend-частини:

- bcrypt-операції є відносно дорогими;
- великі SQL JOIN-запити можуть стати повільними;
- агрегатні запити статистики можуть навантажувати БД;
- створення великих творів із багатьма сторінками може займати більше часу;
- часте оновлення `reading_progress` може створювати багато UPDATE-запитів.

### PostgreSQL

Потенційні проблеми PostgreSQL:

- відсутність потрібного індексу може призвести до повного сканування таблиць;
- часті `COUNT` і `GROUP BY` можуть бути дорогими на великих таблицях;
- JOIN-и з таблицею `comments` можуть сповільнювати статистику;
- текстові поля великого розміру можуть збільшувати розмір таблиць;
- без автоматичних міграцій складніше контрольовано оновлювати схему.

## 12. Рекомендації з оптимізації

### 12.1. Frontend-оптимізації

Рекомендовано:

- залишати `useMemo` для фільтрації та сортування;
- уникати зайвих повторних рендерів;
- за потреби додати debounce для пошуку;
- для великого списку творів розглянути pagination або infinite scroll;
- для дуже великих списків використовувати virtualized list;
- не завантажувати зайві дані на сторінках, де вони не потрібні.

### 12.2. Backend-оптимізації

Рекомендовано:

- логувати час виконання повільних запитів;
- не збільшувати bcrypt salt rounds без потреби;
- використовувати транзакції тільки там, де вони потрібні;
- уникати зайвих SQL-запитів у циклах;
- оптимізувати JOIN-запити;
- додати pagination для коментарів і списків творів;
- перевіряти важкі запити через `EXPLAIN ANALYZE`.

### 12.3. PostgreSQL-оптимізації

Рекомендовано:

- регулярно перевіряти індекси;
- додати індекси для частих фільтрів;
- використовувати `EXPLAIN ANALYZE` для повільних запитів;
- для статистики за потреби використовувати кешування;
- для великих таблиць розглянути матеріалізовані представлення;
- регулярно виконувати backup;
- стежити за розміром таблиць і індексів.

## 15. Узагальнення результатів

Після переходу на PostgreSQL основна продуктивність системи залежить від:

- швидкості SQL-запитів;
- наявності індексів;
- кількості творів, коментарів і користувацьких активностей;
- витрат на bcrypt під час авторизації;
- кількості frontend-рендерів;
- розміру списків, які відображаються на сторінках;
- складності агрегатних запитів для статистики.

Поточна архітектура є достатньою для навчального і невеликого production-сценарію.

Для масштабування системи найважливішими напрямками оптимізації є:

- pagination;
- backend search;
- оптимізація SQL-запитів;
- кешування статистики;
- зменшення кількості зайвих frontend-рендерів;
- моніторинг повільних запитів.

## 16. Висновок

У результаті профілювання визначено, що головні потенційні вузькі місця системи пов’язані з трьома напрямками:

1. frontend-обробка списків творів;
2. криптографічні операції авторизації;
3. SQL-запити до PostgreSQL, особливо JOIN-и та агрегатні запити.

На frontend основне навантаження створюють пошук, фільтрація, сортування та рендер списку творів.

На backend основними дорогими операціями є `bcrypt.hash` і `bcrypt.compare`, а також SQL-запити, які працюють із творами, коментарями, прогресом читання та статистикою.

На рівні PostgreSQL важливо підтримувати правильні індекси, перевіряти важкі запити через `EXPLAIN ANALYZE` і контролювати агрегатні запити сторінки статистики.

Поточна реалізація є достатньо стабільною для невеликого вебзастосунку. Для подальшого розвитку доцільно впровадити pagination, backend search, кешування статистики і регулярний аналіз повільних SQL-запитів.
